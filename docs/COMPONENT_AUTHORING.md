# Component authoring

This is the canonical engineering contract for adding or changing public cards in HA-UI-Components.

The repository is a Home Assistant frontend/HACS Dashboard library. It owns presentation, frontend discovery/composition and direct UI interaction. Persistent backend business logic, reusable server-side state and services belong in [HA-UI-Backend](https://github.com/brayden276/HA-UI-Backend).

## Component categories

Every public component must declare one category in `scripts/public-components.mjs`.

### Presentational

Input-driven visual primitives such as KPI, status, progress, notice and separators. They may be completely static or expose explicitly configured drill-down/navigation actions.

Do not render button semantics merely because the Components dashboard preview historically looked pressable.

### Entity-aware

Cards backed by one or more Home Assistant entities. They derive visible state from `hass.states` and normally support native more-info or a configured direct action.

Examples: Welcome Header, Update Row.

### Direct controller

Cards that call Home Assistant services or backend services. They build stable DOM where practical, derive state from Home Assistant, handle unavailable entities, expose pending/error state and clean up all timers/request queues.

Examples: Split, WLED, Garage Door, Camera, Apple TV, live Control Row and Media Row.

### Registry-driven

Cards that discover areas/devices/entities or generate controls from registry data. Use the shared registry runtime where it already supplies the required data instead of opening an independent duplicate registry stack.

Examples: Favourites, Smart Collection, Room Directory, Household Directory.

### Async visualisation

Cards that request statistics, history, forecasts or other asynchronous data and render visualisations. Guard against stale responses, cache/request-throttle where appropriate and clean up observers/listeners.

Examples: Metric Pair, Solar Daylight, Energy History, History Graph.

### Composition/wrapper

Cards whose main responsibility is to instantiate existing public components and forward configuration/`hass`. They should not duplicate child behaviour.

Examples: Home Overview and Favourites Minimal.

## Source structure

One public component lives in one descriptively named kebab-case file:

```text
src/components/example-controller.js
```

The runtime bundle does not use package imports between source modules. Shared APIs are exposed through library globals and destructured at the top of the module:

```js
const {
  escapeHtml,
  interaction,
  openMoreInfo,
  registerCard,
} = globalThis.__HA_COMPONENT_LIBRARY_SHARED__;
```

The explicit bundle workflow and source validation compose modules according to `src/bundle-manifest.json`: shared modules first, support elements next, then public components. Do not depend on accidental lexical state from another component file.

Never edit `dist/ha-component-library.js` manually. It is generated by `npm run bundle` / `scripts/assemble.mjs`.

## Required class and lifecycle structure

A public component is a custom element with these lifecycle concepts.

### Constructor

Use the constructor for stable instance state and Shadow DOM creation.

```js
constructor() {
  super();
  this.attachShadow({ mode: "open" });
  this.config = null;
  this._hass = null;
}
```

Do not require Home Assistant state in the constructor.

### `setConfig(config)`

Home Assistant calls `setConfig` with Lovelace configuration.

Responsibilities:

- validate required configuration;
- apply defaults without mutating the caller's object;
- invalidate render/request signatures when configuration changes;
- build/render when enough information is available.

Throw a useful error for required fields:

```js
if (!config?.entity) throw new Error("entity is required");
```

Do not use configuration presence to fake an interactive preview. If there is no meaningful action, render non-interactive semantics.

### `set hass(hass)`

Retain Home Assistant on a private/internal field such as `_hass` or `h`:

```js
set hass(hass) {
  this._hass = hass;
  this._render();
}
```

Never assign `this.hass = hass` from inside the setter; that recursively invokes the setter and is rejected by maintainability validation.

For composition cards, forward the current `hass` object to retained child cards rather than recreating children for every state update.

### `connectedCallback()`

Start connection-dependent work that should only exist while the element is connected:

- subscriptions;
- global event listeners;
- `ResizeObserver`/other observers;
- periodic timers;
- deferred initial synchronisation.

It must be safe for a custom element to disconnect and reconnect.

### `disconnectedCallback()`

Stop everything started by the element:

- unsubscribe registry/event subscriptions;
- remove global listeners;
- disconnect observers;
- clear timeouts and intervals;
- destroy `interaction()` handles;
- destroy request coalescers;
- abort/cancel outstanding local confirmation state where applicable.

If a component creates dynamic interactions on each render, destroy those handles before replacing the DOM as well as on disconnect.

`npm run check` performs practical static checks for missing cleanup counterparts.

### `getCardSize()` and grid options

Implement `getCardSize()` for Home Assistant layout estimation. Components that use sections/grid sizing may expose the existing static `getGridOptions()` contract used elsewhere in this repository.

Do not change existing geometry just to satisfy interaction code.

## Render/update strategy

Choose the strategy appropriate to the category.

### Simple/presentational cards

Rebuilding `shadowRoot.innerHTML` is acceptable when the component has little state and no long-lived child/controller DOM.

If rebuilding DOM, destroy prior interaction handles first and rebind the new elements.

### Live/direct controllers

Prefer build-once/update-in-place:

```text
_build()       create stable DOM and bindings once
_model()       derive current model from config + hass
_render()      mutate text/attributes/classes
```

This avoids destroying focus, active gestures, pending controls and modal state when Home Assistant publishes an unrelated state update.

Use a render signature when it meaningfully reduces redundant DOM work. Do not include unstable data that causes unconditional rebuilding.

### Async visualisations

Track a request key/generation. Ignore stale responses when configuration/range changes while a request is in flight. Do not let an older response overwrite a newer requested range.

## Shadow DOM

Public components use open Shadow DOM:

```js
this.attachShadow({ mode: "open" });
```

Keep component styles scoped in the component Shadow DOM. Reuse existing Home Assistant/dashboard CSS variables. Do not create a second colour/spacing/typography system for interaction feedback.

The shared runtime, component specifications and Home Assistant inspect public component Shadow DOM where needed. That is one reason the library standardises on `mode: "open"`.

## Escaping and runtime text

Prefer `textContent` for live strings:

```js
this.nameElement.textContent = name;
```

When interpolating untrusted/config/entity strings into HTML, use the shared `escapeHtml()` helper:

```js
`<span>${escapeHtml(this.config.title)}</span>`
```

Do not implement a local HTML escaping regex. Maintainability validation rejects duplicated escaping implementations.

Attribute values also require escaping when interpolated into HTML.

## Shared helpers

Canonical helpers live under `src/shared/` and are exported through `globalThis.__HA_COMPONENT_LIBRARY_SHARED__`.

Use the existing helper instead of duplicating its behaviour:

- `escapeHtml()` — HTML escaping;
- `navigateTo()` — Home Assistant navigation + `location-changed`;
- `openMoreInfo()` — native `hass-more-info` event;
- `interaction()` — pointer/hold/repeat/keyboard/action feedback;
- `createRequestCoalescer()` — latest-value/intent request coalescing;
- `waitForEntityState()` — shared state-confirmation polling/timeout cleanup;
- `registerCard()` — custom-element/card-picker registration;
- shared registry/runtime modules for area/device/entity discovery.

If several components need the same non-visual behaviour, improve the shared primitive rather than adding parallel private implementations.

## Interaction system

All ordinary user-facing tap/hold/repeat controls use `interaction()`.

```js
this._interaction = interaction(this.button, {
  primary: () => this._toggle(),
  hold: () => openMoreInfo(this, this.config.entity),
  optimistic: false,
  repeat: false,
  feedback: true,
});
```

See `docs/INTERACTION_MODEL.md` for the full API.

Exceptions are controls whose pointer position is itself the value, such as native range inputs and chart scrubbing. These retain native pointer/keyboard behaviour, while backend requests should still use shared coalescing/state-confirmation primitives where applicable.

Do not write a second long-press timer, repeat loop or scroll-cancellation implementation in a component.

## Pending and optimistic state

A Home Assistant service promise resolving means the request was accepted; it does not necessarily mean the resulting entity/physical state has been reached.

### Reversible controls

Lights, switches, media playback, brightness and temperature may render the intended state immediately. Reconcile against Home Assistant state and roll back on error/timeout.

Use the component's existing strong queue if it already represents more semantics than the generic helper. Split temperature is the reference example: local target changes are immediate, backend requests are queued/coalesced, and completion waits for reported target state.

### Physical/slow/irreversible controls

Garage doors, update installation, scripts, maintenance commands and similar actions must not render an unconfirmed successful state.

Examples:

- Garage Door remains pending until its reed sensor confirms the requested physical state.
- Update Row keeps a separate request/start state and 12-second watchdog for `in_progress`/entity-state confirmation.
- Camera maintenance actions remain confirmation-gated and non-optimistic.

### Pending keys

Direct controllers with concurrent actions should use semantic pending keys (`power`, `temperature`, `volume`, entity ID, etc.) so one request does not unnecessarily block unrelated controls.

## Continuous controls

Continuous controls should feel local and immediate even when Home Assistant is slower.

For step controls, use repeat-on-hold and an existing queue/coalescer.

For sliders:

1. update the local output/track on `input`;
2. send values through `createRequestCoalescer()` (or an existing stronger queue);
3. keep only the latest queued intent while a request is running;
4. reconcile against `hass.states`;
5. restore reported state on failure.

Do not emit one independent backend request for every pointer pixel/`input` event.

## Registry usage

Prefer the shared registry/runtime layer already used by Smart Collection, Room Directory, WLED and related cards.

When a shared integration needs to affect dashboard discovery, register an entry filter or control resolver with `shared/dashboard-runtime.js`. Do not replace `uiEntry`, `controlConfig` or a component prototype after registration; those late wrappers are compatibility debt, not an extension mechanism.

A registry-driven card must:

- ignore disabled/hidden entities where appropriate;
- de-duplicate by stable registry/device identity rather than friendly name;
- preserve existing shared registry subscriptions/caching;
- avoid opening duplicate subscriptions to the same registries unless the data contract genuinely differs;
- invalidate cached derived structures when registry update events arrive.

Stable user preferences should refer to stable registry identifiers where possible, not mutable entity display names.

## Unavailable state

Treat missing, `unknown` and `unavailable` states deliberately.

A direct control must not call a service when its target is unavailable. Disable the action and expose a meaningful state string. Do not leave a control enabled because the last known state happened to be actionable.

If more-info remains useful for an unavailable entity, the details identity may remain inspectable while the direct action is disabled.

## Accessibility

At minimum:

- native `<button>` for normal buttons;
- `role="button"` + `tabindex="0"` only when an existing non-button element genuinely must become an action target;
- all icon-only controls have `aria-label` or equivalent accessible naming;
- `aria-pressed` for binary/toggle state where appropriate;
- `aria-selected` for selection/listbox state;
- `aria-busy`/live status for asynchronous action feedback;
- progress uses `role="progressbar"` and determinate value attributes when known;
- unavailable actions use disabled/`aria-disabled` consistently;
- keyboard activation routes through the same action as pointer activation;
- reduced motion never removes information or functionality.

Do not add button semantics to informational content.

## Naming and versioning

Public custom-element type names are versioned explicitly where the existing library uses a version suffix, for example:

```text
component-example-controller-v1
```

Source filenames are descriptive kebab-case and normally omit the version suffix unless the existing source file name is itself version-specific.

The JavaScript class name is PascalCase and matches the public inventory entry:

```js
class ComponentExampleControllerV1 extends HTMLElement {}
```

Do not silently repurpose a published component type for a breaking configuration/behaviour contract. Add a new version when compatibility cannot be preserved.

## When functionality belongs in HA-UI-Backend

Put functionality in HA-UI-Backend when it is server-side state or business logic that should exist independently of one browser/dashboard, including:

- persistent cross-client state;
- authoritative device/room configuration;
- timers/deadlines that must survive browser closure;
- orchestration across entities that should be atomic/reusable;
- services that multiple dashboards/automations should call;
- secure/privileged logic that should not be implemented in browser JavaScript.

Keep frontend-only concerns here:

- presentation and layout;
- state derivation for display;
- more-info/navigation actions;
- frontend interaction feedback;
- registry-driven card composition;
- coalescing local rapid input before calling an existing service.

The Split room registry/timer model is the reference separation: authoritative room data and timer service live in HA-UI-Backend; the component owns interaction/presentation.

## When patches are appropriate

There is no active patch layer. Compatibility work belongs in the owning component or shared runtime; add a separate adaptation only when an external runtime genuinely requires one.

Do not implement a new component feature as a patch merely because patching is a smaller diff.

Before adding a patch, ask:

1. Can this behaviour be fixed in `src/components/<component>.js`?
2. Is the behaviour actually shared and better placed in `src/shared/`?
3. Is the patch preserving compatibility with an external/legacy runtime rather than becoming the normal code path?

If 1 or 2 is yes, do not add the patch.

Any future retained adaptation must document its owner, compatibility reason and concrete removal condition beside the source. It is a transitional compatibility/load-timing boundary, not a normal feature location.

## Adding a public component

The public inventory is centralised in `scripts/public-components.mjs`; there is no separate hard-coded component count to update. It supplies category/profile metadata to generic contracts and automatic specialised-spec discovery. The public compatibility oracle is deliberately independent: do not generate it from the implementation, manifest or runtime registration, because it must catch accidental public type, constructor and picker-metadata changes.

A new public component requires these repository changes:

1. `src/components/<descriptive-kebab-case>.js` — implementation and `registerCard()` call.
2. `src/bundle-manifest.json` — place the component in dependency-safe public-component order.
3. `scripts/public-components.mjs` — add its category/interaction contract.
4. The independent public compatibility oracle — add the public type, constructor and picker metadata.
5. A specialised component specification only when generic contracts cannot describe the behaviour.
6. `docs/components.md` — add configuration and actual interaction behaviour to the catalogue.
7. Any specific shared/support source required by the implementation, only if genuinely reusable/necessary.

For an ordinary behaviour-preserving refactor, edit the relevant `src/` module only. The normal source gate runs generic contracts plus migrated black-box component specifications, so such a refactor should not require checker edits. Change the manifest only to add or reorder source, and do not change the independent compatibility oracle merely to follow an implementation refactor. You do **not** edit `dist/ha-component-library.js`.

Run:

```text
npm run check:source
```

`npm run check:style` remains the blocking style-provenance gate. The normal source command reports existing provenance drift as advisory and never regenerates the independently authored fingerprints.

Before release, use the explicit bundle/release workflow to regenerate the distributable, perform separate freshness checks, then obtain live Home Assistant/HACS proof where the change requires it. Source validation never reads or writes `dist/`.

## Copyable component skeleton

```js
const {
  escapeHtml,
  interaction,
  openMoreInfo,
  registerCard,
  waitForEntityState,
} = globalThis.__HA_COMPONENT_LIBRARY_SHARED__;

class ComponentExampleV1 extends HTMLElement {
  static getGridOptions() {
    return { columns: 12, rows: "auto" };
  }

  constructor() {
    super();
    this.attachShadow({ mode: "open" });
    this.config = null;
    this._hass = null;
    this._built = false;
    this._renderSignature = "";
    this._interactions = [];
  }

  setConfig(config) {
    if (!config?.entity) {
      throw new Error("entity is required");
    }
    this.config = {
      title: null,
      ...config,
    };
    this._renderSignature = "";
    if (!this._built) this._build();
    this._render();
  }

  set hass(hass) {
    this._hass = hass;
    if (!this._built) this._build();
    this._render();
  }

  connectedCallback() {
    // Start subscriptions, global listeners, observers or timers here.
  }

  disconnectedCallback() {
    for (const handle of this._interactions) handle.destroy();
    this._interactions = [];
    // Stop every subscription, observer and timer started by the card.
  }

  getCardSize() {
    return 1;
  }

  _build() {
    if (this._built) return;
    this._built = true;
    this.shadowRoot.innerHTML = `
      <style>
        :host {
          display: block;
          min-width: 0;
        }
      </style>
      <ha-card>
        <button class="control" type="button"></button>
      </ha-card>
    `;

    const control = this.shadowRoot.querySelector(".control");
    this._interactions.push(
      interaction(control, {
        primary: () => this._primaryAction(),
        hold: () => openMoreInfo(this, this.config.entity),
        optimistic: {
          capture: () => this._isVisuallyOn(),
          apply: () => this._setVisualOn(!this._isVisuallyOn()),
          rollback: (previous) => this._setVisualOn(previous),
        },
        repeat: false,
        feedback: true,
      }),
    );
  }

  _model() {
    const state = this._hass?.states?.[this.config.entity] ?? null;
    const stateValue = String(state?.state || "").toLowerCase();
    return {
      state,
      available:
        Boolean(state) &&
        !["unknown", "unavailable"].includes(stateValue),
      on: stateValue === "on",
    };
  }

  async _primaryAction() {
    const model = this._model();
    if (!model.available) return;

    const expected = model.on ? "off" : "on";
    await this._hass.callService("homeassistant", "toggle", {
      entity_id: this.config.entity,
    });
    await waitForEntityState(
      () => this._hass,
      this.config.entity,
      (value) => value === expected,
      { timeout: 9000 },
    );
  }

  _isVisuallyOn() {
    return this.shadowRoot.querySelector(".control")?.getAttribute("aria-pressed") === "true";
  }

  _setVisualOn(on) {
    const control = this.shadowRoot.querySelector(".control");
    if (!control) return;
    control.setAttribute("aria-pressed", String(on));
  }

  _render() {
    if (!this._built || !this.config) return;
    const model = this._model();
    const signature = JSON.stringify([
      model.state?.state,
      model.state?.attributes,
      this.config.title,
    ]);
    if (signature === this._renderSignature) return;
    this._renderSignature = signature;

    const control = this.shadowRoot.querySelector(".control");
    const title =
      this.config.title ||
      model.state?.attributes?.friendly_name ||
      this.config.entity;
    control.textContent = title;
    control.disabled = !model.available;
    control.setAttribute("aria-pressed", String(model.on));
    control.setAttribute(
      "aria-label",
      model.available
        ? `${model.on ? "Turn off" : "Turn on"} ${title}`
        : `${title} unavailable`,
    );
  }
}

registerCard({
  type: "component-example-v1",
  element: ComponentExampleV1,
  name: "Example",
  description: "Description shown in the Home Assistant card picker.",
});
```

For a presentational component, remove the direct-controller action/state code instead of leaving inert buttons. For a composition component, instantiate the canonical child components and forward `hass` rather than copying this controller skeleton wholesale.
